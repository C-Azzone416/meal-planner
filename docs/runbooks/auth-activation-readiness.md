### 1.2 What selects a Preview deploy today

Read from `.github/scripts/classify.sh` and `.github/workflows/ci.yml` (lines 66–81 compute the classifier inputs).

Paths and conditions that set `hosted_preview=true` (all of them also need the trust and enable gates below):

- **Hosted paths:** `web/*`, `api/*`, `hosted/*`, `vercel.json` (hosted_go).
- **`internal/core/*`:** marks hosted_go, local_go and contracts.
- **`contracts/*`:** marks everything.
- **`go.mod`, `go.sum`, `.github/*`:** toolchain, marks everything.
- **Unknown paths:** any path that is not matched by a rule and is not root-level markdown (for example `tools/deploy/*`) marks everything.
- **`CLASSIFY_ALL` fail-safe:** `ci.yml` sets `CLASSIFY_ALL=true` when the base commit is empty, all zeros, missing from the clone, or when `git diff` fails. That selects every component whatever the changed paths were, so even a docs-only or CLI-only push can select Preview in that case.

Paths that normally do **not** select Preview: `docs/*`, root-level `*.md`, and CLI paths (`cmd/*`, `internal/localstore/*`, `internal/mcpadapter/*`), because the classifier decides Preview before CLI changes mark contracts. This holds only when the base is known and the diff succeeds.

Gates that must all hold for a Preview deploy:

- `PREVIEW_TRUSTED=true`: only for a `push` to `refs/heads/develop`. Pull requests (including same-repo ones) and pushes to other branches are never trusted, so **pull requests do not deploy a Preview**.
- `PREVIEW_ENABLED=true`: mirrors the repository variable `vars.PREVIEW_ENABLED`.
- The `preview` job itself requires `hosted_preview == 'true'` and no failed or cancelled needed job, and calls `preview.yml` with the pushed `github.sha`.

Path selection means a deploy is attempted, not that it succeeds.

[hosted-deploy.md](hosted-deploy.md) §2: automatic Preview runs on develop pushes. The summary carries the SHA, URL and manifest (`preview-manifest-<sha>-<run attempt>`).

**There is no routine manual Preview deployment after bootstrap.** `preview.yml` is `workflow_call` only, with no `workflow_dispatch`. The one-time manually dispatched bootstrap (hosted-deploy.md §1) does include a Preview deployment, but its prerequisites forbid auth, env vars and a database, so it must not be re-run with auth enabled or to pick up a new Secret. Whether to add a reviewed manual trigger, or to rely on a qualifying push to develop, is an **owner decision that is pending**. This runbook does not choose it and no new workflow or deployment is authorized here. Re-running an existing eligible `ci.yml` run is different from adding `workflow_dispatch`; it has its own limits (same-SHA, §1.4).

Consequence for env changes: Vercel environment changes apply to new deployments only (UNVERIFIED here; see §6). Until the owner decides, the documented way to pick up a changed Preview setting is the next qualifying develop push.

### 1.4 Verifying the served deployment (identity, not just the SHA)

A matching source SHA does not prove that the alias serves the deployment you intend, or that it carries the changed environment. `preview.yml` (the alias step, around lines 484–492) leaves the alias on the existing deployment when that deployment's recorded SHA equals the one being deployed, even if the new deployment has different env values. It also skips the alias when the candidate is an ancestor of what the alias serves (around lines 503–506). Items 1–7 below are the **identity confirmation**: every target needs all of them, and they are a prerequisite to any acceptance test. Stop on any mismatch and do not test. The state-specific acceptance checks and retirement that follow the list are separate from the identity confirmation and are not prerequisites to it:

1. **Target SHA.** `git rev-parse origin/develop` after the merges in 1.3; confirm with `git merge-base --is-ancestor <#78 merge> <sha>` and likewise for #75.
2. **Run.** Find the `ci.yml` push run for that SHA on develop. Its `preview` job must have succeeded, not been skipped (skipped means the classifier did not select it, a gate was false, or `PREVIEW_ENABLED` was unset). Note the run attempt.
3. **What the repo records.** This is a prebuilt CLI deploy from a build artifact, not a Git-integrated build. The evidence that exists: the build manifest (`preview-manifest-<sha>-<run attempt>`) records `source_sha`, `target`, `lockfile_sha256`, `build_output_tar_sha256` and, after deploy, `deployment_url`. The deployment itself carries custom metadata `meta.sourceSha`, written by `preview.yml` (`--meta "sourceSha=…"`). Do not assume a Git-integration "source commit" field exists or independently attests to this CLI build. `/api/health` does not report a build SHA (hosted-deploy.md follow-up), and a healthy health response alone proves neither SHA nor env revision.
4. **Intended deployment ID.** Record privately the ID of the new deployment created for this change. The stable-alias summary section ("Preview alias") prints Alias, Deployment ID and Source SHA only when the step moved the alias and read-after-write confirmed it. The manifest carries the unique URL but not the ID; otherwise read the ID privately for that unique URL in the Vercel project (UNVERIFIED which console fields show it). The ID must be the new one, not one from an earlier run.
5. **Alias to ID confirmation.** If `PREVIEW_ALIAS` is set, confirm the alias points at that exact ID (the summary's "Vercel API confirms the alias points at this deployment", or the owner's private read of the alias). If the summary instead says "already points at a deployment of <sha>… leaving it" or "skipping the alias", the alias is **not** serving the new deployment: do not test through the alias.
6. **Same-SHA reruns.** A re-run of the same SHA (or a second deploy of it) creates a new deployment but, because of the same-SHA rule, the alias stays on the old deployment. Treat the alias as stale. Test the new deployment through its own unique (protected) URL with the owner's access, or use a new qualifying commit with a different SHA. Never infer env freshness from the SHA.
7. **Applied env state, private.** Record privately that the intended deployment was built after the env change and what the env state was: the names present (never values), the single membership format, the pull stage's guard output with `[SENSITIVE]` markers. Secrets are write-only, so existence and names are the evidence.

After the identity is confirmed (items 1–7), and never as part of it:

- **State acceptance, enabled auth (after activation only).** Run `GET /api/auth-config` and the A3/A6 protected-API checks (R3–R11) against the confirmed deployment (alias if confirmed, otherwise its unique URL), and record which target was checked. Used by 3A.10, 3A.11 and the rehearsal.
- **State acceptance, disabled auth (after a disable or rollback only).** `GET /api/auth-config` returns `enabled:false`, the sign-in form is disabled and protected APIs fail closed (§5 step 3). No enabled-auth success check applies to a disabled deployment.
- **Retirement of stale deployments.** Old deployment URLs and aliases that still carry an older membership or an enabled auth set stay reachable until retired. Keeping an enabled old deployment accessible defeats a disable or a removal on the new one. Retiring them is a separate approved action (3A.13) taken after the new deployment's identity (items 1–7) and state acceptance are confirmed.

## 5. Rollback and disable

**Disable (any environment): remove the complete environment-specific auth set, not a single name.** `tools/deploy/check-pulled-env.sh` (lines 210–218) requires `NEON_AUTH_BASE_URL`, `NEON_AUTH_ENDPOINT_ID` and the membership variable to appear exactly once as a complete set, or none of them at all; a partial set (for example the membership and endpoint ID without the base URL) fails the deployment's pull stage before it can ship. #78's guard keeps this: all or none, with exactly one membership format. Do not edit or weaken the guard to make a rollback pass. Procedure, with approval:

1. Preserve the current values of the whole set privately (a stale list can re-admit a removed member).
2. Remove all three names for that environment in Vercel.
3. Deploy, confirm the **served deployment** identity (§1.4 items 1–7), not just a green job, then run the disabled-state acceptance (§1.4): `GET /api/auth-config` returns `enabled:false` on the confirmed deployment, the sign-in form is disabled and protected APIs fail closed (401/403/503). Confirm the alias points at the new deployment ID, or test its unique URL.
4. Retire old enabled deployment URLs and aliases (3A.13, §1.4 retirement).

This does not delete provider users. Re-enabling later is a fresh 3A.9 activation with a fresh approval.

Preview rollback, in order of least change:

1. Membership wrong or too broad: restore the previous list (recorded privately), keeping exactly one membership format (never both names), deploy, confirm the served deployment identity (§1.4 items 1–7). Removal takes effect on the next protected request on the new deployment (removal bound). Retire old deployment URLs and aliases that carry the old list.
2. Bad provider setting (webhook, key, endpoint): the handler already fails closed; disable by removing the complete auth set (above), deploy, fix the provider side, retest from R1.
3. Unexpected or duplicate user found: stop. Remove the complete auth set as above, confirm Sign-up with Email is disabled, audit, and ask the owner before any user deletion.
4. Exposed bypass secret: revoke and replace immediately; do not reuse a CI credential.
5. Bad code on the alias: the alias moves forward only (hosted-deploy.md "Move-forward rule"); `preview.yml` deliberately skips the alias for a commit that is an ancestor of what it serves, so pushing or redeploying an older good SHA is not a safe rollback path. Use an approved corrective or revert commit on develop (a new SHA that deploys and whose identity is confirmed per §1.4 items 1–7), or, if the alias is stuck, an explicitly approved token-safe alias reassignment to a specific deployment ID per hosted-deploy.md, followed by the exact deployment-ID and auth checks. Retire any older deployment URL that is still enabled and reachable.

Production: stays disabled by default. If ever activated and a check fails, remove the complete environment-specific auth set, deploy through the Production workflow, then confirm `enabled:false` publicly. Do not roll the database back.
