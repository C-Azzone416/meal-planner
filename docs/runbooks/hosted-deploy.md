# Hosted deploy runbook

Operator procedures for the Vercel-hosted web/API. The policy is in [ci-cd-plan.md](../ci-cd-plan.md); this page only says how to run the workflows. Nothing here is done automatically, and every Vercel-touching run needs explicit approval at the time.

Workflows: `.github/workflows/vercel-bootstrap.yml` (one time), `preview.yml` (called from `ci.yml` on `develop` pushes), `deploy-production.yml` (manual).

## Build/deploy split

In every workflow, `vercel build` (which runs repository install and build scripts) never runs in a job that has `VERCEL_TOKEN`. Each target runs as three jobs:

1. **pull**: has the token and no checkout during the token step, so no repository code is present next to `VERCEL_TOKEN`. Runs `vercel pull`, then checks out only `tools/deploy/check-pulled-env.sh` from the workflow's own commit (`github.workflow_sha`, never the SHA being built), checks and deletes the pulled env files (see the guard below), and uploads only `.vercel/project.json` (project/org IDs and the pulled project settings) as a one-day artifact for the build job.
2. **build**: no token. Checks out the exact SHA, restores `project.json`, writes a placeholder env file (see below), runs `vercel build`, then `tools/deploy/materialize-output.sh` (see "Self-contained build output" below), tars `.vercel/output` and `.vercel/project.json`, and records the tarball's SHA-256 as a job output.
3. **deploy**: has the token, runs on a fresh runner with only `tools/deploy` checked out (from the commit that defines the workflow, not the built SHA). Downloads the tarball, verifies its checksum against the build job's output, then `tools/deploy/safe-extract.sh` validates it before anything is written: every entry must be a regular file or directory (symlinks, hardlinks and special files are rejected), no name may be absolute or contain `..`, and only `.vercel/output` and `.vercel/project.json` are allowed. It extracts into a fresh empty directory under `$RUNNER_TEMP` with `--no-same-owner --no-same-permissions`. Then `materialize-output.sh --check` fails the job if any extracted `.vc-config.json` still has a non-empty `filePathMap`. Only then is the pinned Vercel CLI installed (into another `$RUNNER_TEMP` directory, not the npx cache, so the archive cannot touch it) and `vercel deploy --prebuilt` run from the extraction directory, followed by the smoke test. `tools/deploy/safe-extract_test.sh` covers the symlink, hardlink, `..`, absolute-path, fifo and clean-archive cases.

**Self-contained build output.** `vercel build` does not always copy a function's files into its `.func` directory. For a file outside it, such as the compiled Go binary (the Go builder leaves it in the build runner's `/tmp`), it writes `filePathMap` into `.vc-config.json`: `{"bootstrap": "<source path relative to the project root>"}`. Only the map is shipped; the file stays on the build runner. The bootstrap run proved the consequence (run 41766559492, vercel 65.9.0): the artifact held `functions/api/health.func/.vc-config.json` with `"filePathMap":{"bootstrap":"../../../../../tmp/77f3c1/bootstrap"}` and no binary, and `vercel deploy --prebuilt` on the deploy runner failed with `ENOENT: no such file or directory, readlink '/tmp/77f3c1/bootstrap'`. A single job running build and deploy on one machine never sees this. Reproduced locally with `vercel@65.9.0 build` and no login: the same shape (`filePathMap.bootstrap` pointing into the OS temp dir through `../..` steps).

`tools/deploy/materialize-output.sh` runs in each build job after `vercel build` and before packaging. For every `.vc-config.json` with a non-empty `filePathMap` it resolves each source (the project root joined with the map value, which may contain `..`), requires a regular file reached without a symlink (the file itself, and every directory above it, which is checked by comparing the lexical path with `pwd -P`; the build runner's `/tmp` is a real directory, so a symlinked source directory is refused rather than followed), copies it to the map key inside the `.func` directory keeping its mode (the Go `bootstrap` must stay executable), and deletes `filePathMap`. The key is deleted, not emptied: the consumer (`deserializeFunctionEntry`) hydrates only `if (functionConfig.filePathMap ...)` and then spreads the config into the `Lambda`, and `{}` is truthy, so an empty map would be spread in. The key must be relative with no `.`, `..` or empty component and must stay inside the `.func` directory. Afterwards it asserts that no `.vc-config.json` anywhere under the output has a non-empty `filePathMap` and that nothing under `.vercel/output` is a symlink (safe-extract would reject one anyway). The script comes from the commit that defines the workflow (`github.workflow_sha`), checked out after the build, so it also works when the built SHA predates it. `materialize-output_test.sh` (run in CI) covers the real-failure fixture, several functions and entries, each rejection, and the injected tool failures. Each `.vc-config.json` must be exactly one JSON document (a second document after a clean one is refused, in both modes). The rewrite keeps the file's mode. Any anomaly, including a failing `find`, `sort`, `jq`, `cp` or `mkdir` (the tests inject a failure into every call of each), fails the build job with an `::error::` message, and the map is never dropped unless every entry it listed was copied.

This build-side script is a correctness tool, not a security boundary: the build code already owns the build runner and could write anything into the output. The boundary is on the deploy side: the checksum, `safe-extract.sh`, `materialize-output.sh --check` and the token reaching only the deploy job. Known limit: Vercel can alias several routes to one function with a `.func` symlink; that would fail the symlink check here and in `safe-extract.sh`. Nothing uses it today.

The source references (vercel 65.9.0 npm tarball, read as data; the bundles are minified, so the line is the bundle line and the function name finds it):

- Writer: `dist/chunks/chunk-E5CN62HO.js:7`, `filesWithoutFsRefs2` and `writeLambda`. Each `FileFsRef` becomes `filePathMap[<path in function>] = relative(repoRootPath, file.fsPath)`; `repoRootPath` is the project root the build ran in, which is `/home/runner/work/meal-planner/meal-planner`, so `/tmp/77f3c1/bootstrap` is `../../../../../tmp/77f3c1/bootstrap`. Every `FileFsRef` (a file that already exists on the build runner's disk) is mapped this way, not copied; other file kinds (in-memory blobs) are downloaded into the `.func` directory.
- Consumer: `dist/commands/deploy/index.js:22`, `deserializeFunctionEntry` calls `hydrateFilesMap(files, filePathMap, repoRootPath, ..., prebuilt)`, which joins `repoRootPath` with each value and calls `validatePrebuiltFilePath(fsPath, rootPath, ..., enableDanglingSymlinks=true)`. That does `realpath`, and on `ENOENT` a `readlink` of the same path: this is the call that throws the observed `readlink` error (the deploy runner's project root is `$RUNNER_TEMP/deploy-src`, five levels below `/`, so the value resolves to `/tmp/77f3c1/bootstrap`). It also throws `INVALID_PREBUILT_FILE_PATH` ("must be inside the uploaded project") when the resolved path is outside the root, so a `/tmp` source would fail there even if it existed. The same bundle's `describeDeployment` and `prepareContinuation` read `filePathMap` too.
- `dist/chunks/chunk-OZPBJWYU.js:21`, `buildFileTree` (the file collector for `--prebuilt`) joins the project root with each value and ignores entries that resolve outside it (`Ignoring "filePathMap" entry ... resolves outside the deployment root`, debug output only), so a path of this kind is never uploaded either. An output with no `filePathMap` needs none of these paths: the files are in the `.func` directory, under `.vercel/output`, inside the project root.

Not verified: the exact call chain from `vercel deploy --prebuilt` to `hydrateFilesMap` was not traced (the observed error matches `validatePrebuiltFilePath` and nothing else in the bundle); whether the deployed function then starts is only proven by the next bootstrap run. The materialize script and the tests were run offline only. `materialize-output.sh` was also run against a real `vercel build` output (see the PR).

**Alternative: `vercel build --standalone`.** 65.9.0 has this flag (`dist/commands/build/index.js:11`; `VERCEL_EXPERIMENTAL_STANDALONE_BUILD=1` is a deprecated spelling). In the source its only effect on the output is in `filesWithoutFsRefs2`: with it set, `FileFsRef`s are copied into the `.func` directory instead of being mapped, and files under symlinked directories are skipped. It applies to every builder's functions (not just Go) and trades references for copies, so function directories and the artifact can grow; the source shows no use of it for static files. It was not chosen because it cannot be tested offline here, its effect on the Go and Node builders is untested, and the script gives a check that fails with a clear message. It is a possible follow-up; if adopted, keep the deploy-side `--check`.

Production adds a final `tag` job (write-capable GitHub token, no Vercel token) that pushes the annotated tag after the smoke test passes.

**Two approval prompts per production deploy.** `pull` and `deploy` each reference the `production` environment, and both hold the token, so each waits for a required-reviewer approval: first `pull`, then (after `build`) `deploy`. Approving only `pull` does not release the deploy job. This is deliberate: environment secrets are released per job, so the second prompt is a separate chance to check the build output before the token meets it. The bootstrap's production-class half behaves the same way.

**Env files never leave the pull job.** `vercel pull` writes `.vercel/.env.<target>.local`, and that file includes `VERCEL_OIDC_TOKEN`, a live credential valid for about 12 hours. Artifacts on a public repository are readable by anyone, so the pull artifact contains only `.vercel/project.json`, and the env files are deleted from the runner right after the guard runs.

**Env guard (temporary).** `tools/deploy/check-pulled-env.sh` (tested by `check-pulled-env_test.sh` in CI) parses the pulled env files as dotenv and fails the `pull` job if any name or value is outside the narrow deployment allowlist. That list contains `VERCEL_*`, the exact Vercel system names `VERCEL` and `CI`, five exact Vercel-injected build settings, and exact per-environment auth runtime names documented in [authentication.md](authentication.md) (currently configured only in Preview). `VERCEL_OIDC_TOKEN` itself passes because it is a system variable, and is why the pulled files are never shipped.

The build settings are `NX_DAEMON` (value must be exactly `false`; a reply in the Vercel Community that appears to be from Vercel staff, Pauline P. Narvas, 2025-04-21, says Vercel sets it, and the quoted `"false"` came from the poster's `vercel env pull` output), `TURBO_CACHE` (Turborepo `--cache` syntax: `local` or `remote`, each with `rw`, `r`, `w` or an empty action, comma-separated, such as `remote:rw` or `local:,remote:r`, at most 32 characters) and `TURBO_DOWNLOAD_LOCAL_ENABLED`, `TURBO_REMOTE_ONLY`, `TURBO_RUN_SUMMARY` (one of `true`, `false`, `1`, `0`; this set is a guess). `vercel pull` writes whatever the pull API returns. The Turborepo docs give the meaning of all four `TURBO_*` names and the syntax only for `TURBO_CACHE`; Vercel does not document that it sets them or to what, and that it does is inferred from our own pull and the vercel 65.9.0 CLI code path.

The auth runtime names are `NEON_AUTH_BASE_URL`, `NEON_AUTH_ENDPOINT_ID`, and exactly one of `AUTH_ALLOWED_EMAIL` (legacy single member) or `AUTH_ALLOWED_EMAILS` (private JSON membership array). The URL, endpoint and chosen membership name must each appear exactly once as a complete set. `AUTH_ALLOWED_EMAILS` must be a Vercel Secret: the pull guard accepts only the exact redacted `[SENSITIVE]` marker, never a literal list. Runtime validates the actual array as documented in [authentication.md](authentication.md). When a literal Config value is available, the base URL must use the current HTTPS Managed Neon Auth AWS hostname shape and exact `/neondb/auth` path; the endpoint ID must be a lowercase `ep-` DNS label and match the endpoint label in the URL; the legacy email must be a conservative lowercase ASCII address no longer than 254 bytes.

The original three values are currently Vercel Secrets; the new `AUTH_ALLOWED_EMAILS` setting must also use Secret type when adopted. Vercel's current Secret type is write-only after saving and unavailable to Preview/Production pulls. The pinned vercel@65.9.0 CLI's `envPullCommandLogic` writes the exact non-secret marker `[SENSITIVE]` for each unavailable Secret; develop run 42252610081 confirmed all three values were replaced and the CLI logged only their count. The guard accepts that marker for the exact auth names and still requires the URL, endpoint and exactly one membership format. This proves the approved settings exist but cannot prove their saved values. The post-deployment allowed/denied auth smoke tests are the end-to-end value check; a bad value must leave authentication fail-closed. The guard continues to validate literal URL, endpoint and legacy single-email values if those names are later stored as Config; literal multi-member configuration is refused. The workflow deletes the pulled env file before uploading only `.vercel/project.json`, so the build job never receives the account identifier or provider endpoint.

A value outside its set (or empty, or multi-line) fails with `line N: NAME has an unexpected value`, and the value, its length and its prefix are never logged. If a live pull fails, adjust the constraint in the script and its tests only with evidence. The Vercel build settings are not applied to `vercel build`: the build job receives no pulled env (only the placeholder below), so Nx and Turborepo run with their own defaults there, not Vercel's cache settings. The guard exits 1 for an unexpected name or value, an incomplete or inconsistent auth set, a line it cannot parse (an unterminated quote, a lone CR, a NUL byte, a non-uppercase name, an unquoted value starting with `=`), or a `.env*` entry that is a symlink or not a regular file; it exits 2 for a usage or I/O error. It logs names with line numbers and, on a pass, the allowlisted exact non-`VERCEL_` names present; it never logs values or unparseable lines. A failure means the env handoff design must be revisited; do not just loosen the guard. It fails loudly (exit 2) if `find` cannot run, a file cannot be read, or an argument such as `.vercel` is missing. A line that is only uppercase letters, digits and underscores followed by `=` parses as a name with an empty value, so if it is outside the allowlist its text is printed as the name. Add a name only with a citation, as an exact name, and give any non-`VERCEL_` name a value constraint.

**Placeholder env file (unverified).** `vercel build` looks for `.vercel/.env.<target>.local` and, with `--yes` and no file, would try to pull it itself, which needs a token the build job must not hold. So the build job writes a stripped file containing a comment and `VERCEL_ENV=<target>`, nothing else. This has not been verified against a live build, and the Vercel docs do not say what `vercel build` requires. The first bootstrap run is the test; if the build rejects it, revisit the design instead of shipping env values through an artifact.

## Token rule

`VERCEL_TOKEN` is currently a **repository** secret, so any workflow could request it. Until it is moved into the `preview` and `production` environments (a separate approved credential action):

- Pass it only through `env:` on the exact steps that run the Vercel CLI or call the Vercel API (`vercel pull`, `vercel deploy`, deployment ID lookup, production alias check, bootstrap record verification).
- Never give it to a job that checks out the repository or runs install or build scripts (`vercel build`), nor to third-party action, smoke, or artifact steps.
- Never echo it, put it on a command line, or write it to a summary, artifact or cache. The only artifact with pulled `.vercel` data is the one-day pull artifact described above.
- Add no new workflow that reads it without review.

## Deployment Protection bypass secret

`VERCEL_AUTOMATION_BYPASS_SECRET` lives **only in the `preview` GitHub environment**. It is not in the `production` environment, not a repository secret, and no production job reads it. `ci.yml` calls the reusable Preview workflow with `secrets: inherit`, matching Packed Smart; the called deploy job binds `environment: preview`, so the bypass remains environment-scoped rather than being copied to repository scope.

- **What it is.** Vercel's "Protection Bypass for Automation" secret, sent as the `x-vercel-protection-bypass` header. It bypasses Vercel *Deployment Protection*, not application authentication, and it works for **every deployment of the project**, not just previews. Treat it as sensitive.
- **Where it is configured.** Generate it in Vercel under Settings > Deployment Protection > Protection Bypass for Automation, then store it with `gh secret set VERCEL_AUTOMATION_BYPASS_SECRET --env preview`. Meal Planner has a separate project-specific secret installed in the `preview` environment; workflows can verify only its metadata and runtime availability, never its value. When unavailable, smoke tests send no header and protected-URL smoke fails closed.
- **Preview.** The `deploy` job in `preview.yml` (environment `preview`) reads it only in the unique-URL and stable-alias smoke steps' `env:`. The caller inherits its secrets context rather than maintaining a restrictive reusable-workflow whitelist; the called job's environment supplies the preview-only bypass. Preview deployments run merged code pushed to `develop` (never pull-request code) and that code receives the header, so this relies on trusting whoever can push to `develop`.
- **Bootstrap.** The production-class phase deploys with `--skip-domain`, so only its protected unique URL exists and its smoke test really needs the bypass. That smoke test is its own job, `smoke-production-class`, under `environment: preview`. It holds **no Vercel token**, has no checkout and no CLI, only `curl` with the header passed through `-K -` on stdin, and re-validates the URL (`^https://[a-z0-9-]+\.vercel\.app$`) it receives as a job output because it is a new trust boundary. It adds one more `preview` approval prompt if reviewers are ever set on `preview`. Its secret and the token never meet in one job.
- **Production.** `deploy-production.yml` has no bypass secret. After `vercel deploy --prod` it finds the project's public production alias from the Vercel API, polls until the API says the alias points at **this deployment's ID**, then smoke-tests `https://<alias>/api/health` with no bypass header, which proves normal public access. The alias and deployment ID are recorded in the job summary. If no alias is found or the ID never matches (3 minute timeout), the job fails closed and no tag is pushed. The ID check, not the 200, is what proves the alias serves the new build.
- Smoke-test response bodies written to the job summary are capped at 2 KB, stripped of non-printable characters and backticks, and fenced.

Follow-up (app change, not part of the deploy workflows): `/api/health` should report the build commit SHA so smoke can assert it directly.

## 1. One-time bootstrap

Vercel treats a new project's first CLI deployment as Production, even when Preview is requested. The bootstrap proves both targets before automatic Preview is enabled.

Dispatch from `main` with a SHA reachable from `origin/main`; the validate job rejects anything else. Prerequisites: a reviewed SHA of the disposable hosted slice (`api/health.go`, `web/`, `vercel.json`) with no database, Auth, migrations or env vars; Vercel Git integration still disconnected; `PREVIEW_ENABLED` unset; separate approval to run this.

1. Actions > **Vercel bootstrap** > Run workflow. Enter the full 40-character `sha` and `confirm` = `bootstrap`.
2. Approve the `production` environment deployments when prompted (twice: pull and deploy, `--prod --skip-domain`).
3. The `smoke-production-class` job runs under `preview` (token-free, uses the bypass secret) and smoke-tests the unique URL. Then the preview phase deploys the same SHA with `--target=preview`.
4. Read the run summary. For each deployment it must show: a successful, non-empty, unpaginated production-domain inventory, project ID matches, `meta.sourceSha` matches, the expected target, `READY`, no production-domain alias (for the production-class deploy, an empty `alias` list), and a passing smoke test on the unique URL. `aliasAssigned` is diagnostic only because Vercel can report it as `true` for a `--skip-domain` deployment whose authoritative `alias` list is empty. A failed, invalid, empty, or paginated domains fetch fails verification rather than weakening the alias check; names returned by the project endpoint cannot substitute for a complete domains response.
5. Only if both jobs pass, set repository variable `PREVIEW_ENABLED=true`. If either fails, leave it unset, do not retry blindly, and update the plan from current Vercel guidance.

The bootstrap creates no tag and touches no database or environment variables. If the unique URL returns 401/403, Vercel Deployment Protection is blocking it; resolve that as a project-setting decision before retrying.

## 2. Preview

Automatic Preview runs from `ci.yml` on every push to `develop` that changes hosted code, once `PREVIEW_ENABLED=true`. Pull requests run checks only and never deploy a Preview. Nothing to run by hand. The Preview summary carries the SHA, URL and manifest; the manifest is also an artifact named `preview-manifest-<sha>-<run attempt>`. A Preview failure blocks `CI / required`. Every develop commit deploys (`concurrency` group `preview-<sha>`, `cancel-in-progress: false`); nothing is cancelled. Overlapping runs are safe because the alias only moves forward (see below).

**Stable alias.** Set the repository variable `PREVIEW_ALIAS` (e.g. `gh variable set PREVIEW_ALIAS --body meal-planner-develop.vercel.app`) to have each successful develop Preview moved to that hostname after its smoke test. The run summary's "Preview alias" section shows the confirmed deployment ID. Unset skips the step with a notice. It fails if the value is a production domain of the project or does not point at the new deployment within 3 minutes. The alias hostname must be on a domain the Vercel token's scope can manage. The production-domain guard covers this project's domains only (it fails closed above 100 domains).

**Move-forward rule.** Before assigning the alias, the step reads which deployment it points at and that deployment's `meta.sourceSha`. A missing alias (404) or an unknown source SHA means move. For the same SHA, the exact same deployment ID is idempotent. A different deployment replaces it only when both provider records match the expected project/source/IDs, are READY and nonproduction (`target` explicitly null or `preview`), and the candidate has a strictly larger valid integer `createdAt`. Missing/invalid metadata fails closed; equal or older creation times leave the alias unchanged. This permits a same-source rebuild to pick up refreshed Preview runtime configuration without moving backward to an older same-SHA deployment. Otherwise it fetches `develop` history (unauthenticated, blob-less, nothing checked out) and skips with a notice if this run's commit is an ancestor of the one the alias serves, so a late older deploy can't take the alias back and a commit that never deployed (docs-only, failed CI, preview off) never blocks a later one. Any other result (API error, commit not in `develop` history, fetch failure) fails the step. The fetch needs the repository to stay public; if it goes private the step fails closed. Assignment uses `POST /v2/deployments/{id}/aliases` rather than `vercel alias set`, because the CLI performs a user lookup that project-scoped tokens cannot use. The token reaches the REST call only through curl config on stdin, the response must confirm the requested alias, and the existing read-after-write poll must confirm its deployment ID. A second protected smoke test must then get HTTP 200 with `{ "status": "ok" }` from `https://$PREVIEW_ALIAS/api/health`; this proves the stable URL, not only the unique deployment URL.

**Red develop CI.** A red `CI / required` on a develop commit can mean "deployed, but the alias was not moved" (alias step failed). Check the run's alias step and summary before redeploying.

**Alias stuck after a force-push to `develop`.** The move-forward rule fails closed when the commit the alias currently serves is not in `develop` history (for example after a force-push removed it), and every later run then fails the same way. After approval, reassign the alias by hand to the newest good Preview deployment. Use the deployment ID from that run's Preview summary, replace the placeholders, and omit `teamId` for a personal account. Run on a trusted machine with the existing token in the environment; never put the token in command arguments or enable shell tracing.

```bash
# begin token-safe preview alias repair
set +x
: "${VERCEL_TOKEN:?Set VERCEL_TOKEN through the approved secret mechanism}"
printf 'header = "Authorization: Bearer %s"\n' "$VERCEL_TOKEN" |
  curl -fsS --max-time 30 --config - --request POST \
    'https://api.vercel.com/v2/deployments/<deployment-id>/aliases?teamId=<team>' \
    --header 'Content-Type: application/json' \
    --data '{"alias":"<PREVIEW_ALIAS>"}'
# end token-safe preview alias repair
```

Confirm with `GET /v4/aliases/<PREVIEW_ALIAS>` using the same stdin-header pattern, then re-run the failed develop job or push the next commit. Do this from a trusted machine, not a workflow. `tools/deploy/runbook-token_test.sh` executes this example with a fake curl and a synthetic token to check that authentication reaches stdin but never argv.

## 3. Production release

1. Merge the release branch to `main` and wait for push CI on the final `main` commit to finish green (`CI / required`).
2. Pick the SHA: the full 40-character SHA of that final `main` commit (`git rev-parse origin/main`).
3. Pick the version: `app-vMAJOR.MINOR.PATCH`, not already used as a tag (this is the hosted web/API version, separate from CLI/MCP versions).
4. Actions > **Deploy production** > Run workflow, **from `main`**, entering `sha` and `version`. Leave `allow_non_tip` false (default).
5. The verify job rejects the run unless the SHA is reachable from `origin/main` and is its current tip (an older ancestor is refused unless `allow_non_tip` is `true`, for a deliberate rollback-by-redeploy), the tag is unused (checked with `git tag -l` after a full-history checkout), and the newest `ci.yml` push run on `main` for that SHA has a successful `required` job. Fix the input rather than working around it.
6. A required reviewer approves the `production` environment (once for `pull`, once for `deploy`). Check the summary's SHA and version before approving; production secrets are released only after approval. Recommended: restrict the `production` environment's deployment branches to `main` (configured separately, not by these workflows).
7. The pull, build and deploy jobs (see the build/deploy split above) deploy that SHA with `--prod`, wait for the production alias to point at the new deployment ID, smoke-test `https://<alias>/api/health` without a bypass header, then the tag job pushes the annotated tag. The summary records the deployment URL, the production alias, the Vercel deployment ID and the manifest (SHA, lockfile hashes, tool versions, build-output checksum).

Runs are serialized (`production` group, never cancelled). A third request queued while one waits replaces the older queued one, so re-dispatch if a request is dropped. No database migrations run during deployment. Reviewed schema files under `hosted/migrations` ship as source only and require separate owner-approved manual activation in [the recipes runbook](recipes.md). The legacy `db/migrations/**` guard reserves that path for a future reviewed runner; it is not an all-SQL presence check.

## 4. Deploy or smoke failure

- Failure before `vercel deploy`: nothing was deployed. Fix and re-dispatch. No tag exists.
- Smoke failure after a production deploy: the new deployment may already serve the production domain, and no tag was created. Decide explicitly; the preferred action is to roll traffic back to the prior verified deployment:
  1. Find the last good deployment (Vercel dashboard > Deployments, or the previous release's summary URL).
  2. `vercel rollback <deployment-url-or-id>` (or **Instant Rollback** in the dashboard) using an operator credential. Do not add a rollback step that spreads the token.
  3. Confirm the production domain's `/api/health` returns 200 and the prior version.
- Schema: never roll a database back automatically. With expand-and-contract migrations the previous deployment stays compatible, so roll traffic back and roll forward with a reviewed corrective migration.
- After recovery, re-dispatch with the same `version` (no tag was created) or a new one, from a fixed `main` commit.
- Tag push failure after a successful deploy: the deployment is live and verified. Create the annotated tag manually on that SHA after checking the summary, or re-dispatch only if you accept a redeploy.
